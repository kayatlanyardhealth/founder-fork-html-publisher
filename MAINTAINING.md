# Maintaining this repo

For the person who **publishes** this tool, not the people who fork it.

Every fork of this repo must be able to take updates with one click of GitHub's **Sync fork** button. That only works if upstream and downstream never write to the same files. This document records which files are which. Breaking the rule breaks updates for every fork at once, silently, and they'll only find out when they try to sync.

## The ownership split

**Tool-owned — patch these freely:**

```
server.js
scripts/generate-index.js
.github/workflows/
README.md
package.json
.gitignore
MAINTAINING.md
```

**Fork-owned — NEVER commit to these after the initial release:**

```
site.config.json        forks edit this to brand their instance
protected.json          forks edit this every time they gate a document
index.html              regenerated by the Action on every publish
proposals/              every document a fork publishes
```

All four are verified conflict sources. Editing any of them upstream produces a merge conflict on every fork that has diverged — which is all of them, immediately, since publishing a single document counts as divergence.

## Why this stays sustainable

The obvious pressure is: *"I need to add a config option, so I'll add a key to `site.config.json`."*

Don't. `scripts/generate-index.js` holds a `DEFAULTS` object and merges the fork's config over it:

```js
return { ...DEFAULTS, ...parsed, theme: { ...DEFAULTS.theme, ...(parsed.theme || {}) } };
```

A new key added to `DEFAULTS` works immediately on every fork, whether or not their `site.config.json` mentions it. Add the key to `DEFAULTS`, document it in the README, and leave `site.config.json` alone. Forks opt in by adding it themselves.

The same reasoning covers `protected.json` — it is deliberately just `{"gated": []}` with no comments or schema fields, so there is never a reason to edit it.

And `index.html` is fully derived. To change how the index looks, edit the template inside `scripts/generate-index.js`. Every fork picks it up on their next publish. Editing `index.html` directly accomplishes nothing and breaks syncing.

## Before shipping a patch

1. `git diff --name-only` against the last release
2. Confirm every path is in the tool-owned list
3. If a fork-owned file appears, stop and find another way

## Verifying

Run the fork-sync audit: build the repo at its last release, clone it, make realistic fork-side commits (publish a document, edit the config, gate something), commit the patch upstream, then merge. A clean merge with fork data intact is the pass condition.

## Shipping

Push to `main`, then draft a release tagged `vX.Y.Z`. Write the notes by hand — auto-generated notes are built from merged pull requests, and this repo is pushed to directly.

Forks watching this repo for Releases get an email. Everyone else finds out when you tell them.
